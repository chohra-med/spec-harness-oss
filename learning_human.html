Spec Harness · read me first

Let the AI do the typing.
Keep the judgment yours_

Spec Harness is a small set of files you add to a project. They give an AI coding agent a memory of your codebase, rules taken from your own source, and a fixed way of working: one agent writes, a different one checks, and nothing ships without you.

Quick guide · two minutes

What you get

Nothing here is a promise about the future. Each item is a file or a result you can open.

After setup

Rules written from your own code

A RULES.md where every rule names the file and line it came from, labelled as observed or as a recommendation. You review it like a pull request.

After setup

A memory the agent reads first

A short description of the project, its architecture, its stack and what is in progress, plus an inventory of your packages. A new session no longer starts cold.

After setup

A skill for each technology you use

For example one for React Native or one for your API layer: how this project uses it, with the lines that show it.

On every ticket

A goal written before the code

One to five true-or-false checks. This is what "done" means, in writing, before anyone types.

On every ticket

A change with a test that failed first

Written by one agent on a cheap, fast model.

On every ticket

A verdict from someone else

RESULT: PASS or FAIL, with evidence for each check, from a separate agent that never saw the code being written.

Over time

Fewer repeated mistakes

A correction becomes a proposed rule. You say yes or no. Approved rules are read on every later ticket.

Always

The last word

Nothing is committed, pushed or merged without you saying so. Installing never edits your application code.

Start in five steps

About half an hour on a real project, most of it reading what step three wrote.

  1. Start on a branch

    There is no uninstall command. The branch is your undo.

    git switch -c chore/spec-harness

  2. Stage the files

    From the root of your project. It copies files and reports PENDING, which is correct: nothing has read your code yet. Your own CLAUDE.md or AGENTS.md is never overwritten.

    npx -y github:chohra-med/spec-harness-oss init . integrate

  3. Let it read your code

    Open the project in Claude Code, on your strongest model, and type:

    /sdd init

  4. Review what it wrote, then commit

    Read the generated RULES.md the way you would read a pull request from a new colleague. Is each rule true of this codebase? Does the cited line show it? Delete what is wrong. Then commit.

  5. Give it a first small ticket

    Paste the full text of a real, low-risk fix. A title is not a ticket.

    /sdd Free shipping should start at exactly 50.00, not above it. Add a test for an order of exactly 50.00.

    You get one file describing the goal, a change with a test that failed first, and a verdict from a separate agent. You commit it yourself.

No npx, a team, or a large app? The full guide is docs/GETTING-STARTED.md in the Spec Harness repository, with a git clone route and how to undo everything.

02 / The problem

Three things go wrong when an agent works alone

Every session

It starts cold

A new chat knows nothing about your project. It guesses file names, invents helpers that do not exist, and ignores conventions it never saw.

The fix: a memory bank and an inventory of your code that every role reads first.

Every change

It marks its own homework

The agent that wrote the code is the one telling you it works. It has every reason to believe itself, and it does.

The fix: a separate agent, with a fresh context, checks the work against a goal written before the code.

Every week

It repeats the mistake

You correct it today. Next Tuesday it does the same thing, because nothing kept the correction.

The fix: a learner that turns a correction into a rule, after you approve it.

04 / Models

Plan with the best model. Build with a cheap one. Review with what you can afford.

Roles ask for a tier, never a model name. One table in the project maps tiers to models, so changing provider means editing one column. Move the budget and see what changes.

A plan carries the detail, so the model that executes it can be cheaper. If a model is not available, the run uses the nearest tier and says so. It does not stop.

05 / In your repository

What lands in your project

Installing copies files. It never edits your application code and adds no dependency. Click a layer.

06 / The loop

How it gets better instead of repeating itself

Every pass through this loop leaves the project's rules a little sharper. The one step that is always yours is the teal one.

What the learner may do

  • Record a correction or a decision in the project memory.
  • Notice when the same cause shows up twice.
  • Propose one change to one rule or one project skill, with the evidence.

What it may not do

  • Edit your application code.
  • Apply a rule you have not approved.
  • Turn a one-off into policy.

07 / Evidence and limits

Why trust it, and where it is weak

Measured on real runs

  • The verifier does not take the writer's word. On a one-character fix, the checking agent put the old code back in a scratch copy, watched the new test fail, and only then said PASS.
  • Independent reviewers agree on real defects. On one tooling change, three separate agents on three different models each stopped the work on the same unformatted line the writer had not been able to check.
  • The learner asks first. After a ticket it wrote down the decision, proposed changes with before and after text, and applied none of them without a person present.
  • Agents can follow it cold. An agent given only the repository's AGENTS.md found uncommitted work in a project, stopped, and changed nothing.

Honest limits

  • Setup is thorough, not light. On a tiny repository it writes more harness than you have code. It pays off on a real codebase.
  • A green check is not a quality verdict. The structural check proves hashes and citations line up. Only a reviewer finds a wrong rule.
  • Editing a generated rule costs a refresh. Batch your review edits.
  • It needs a capable agent. The shell only copies files; the thinking is done by the model you bring.

08 / Words

The vocabulary, in plain terms

Ticket

The full text of one piece of work. The harness refuses a bare title, because a title is where invented requirements come from.

Goal

A short list of true-or-false checks written before any code. The verifier checks these, line by line. "Tests pass" is necessary, not enough.

Role

One agent file with one job and a limited set of tools: planner, implementer, tester, verifier, reviewer, merger, learner.

Fresh context

A new agent that has not seen the conversation in which the code was written. It cannot be talked into agreeing by a history it never read.

Tier

The class of model a role asks for: strong, fast or review. The mapping to real models lives in one table per project.

Small fix, also called MICRO

One bounded, reversible, local change. It runs as one file, one implementer and one verifier. If it grows or touches shared or sensitive code, it is promoted to the full route.

PENDING and READY

PENDING means files are in place and a model or a reviewer still has work to do. READY means the structural check passed. Neither means "correct"; that is what review is for.

Memory bank

A handful of markdown files under .memory/: what the project is, how it is built, what is in progress, which decisions were made and why.
