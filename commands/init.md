# Command: `init`, source-grounded project initialization

> Initialization stages the harness, then uses an available capable model to derive project-scoped rules, skills and SDD role bindings from the selected project's inventory, existing policies and actual representative code. Shell scaffolding alone stays PENDING.

## Invocation

```text
spec-harness install <path> [new|integrate] [name]   # with no install: npx -y github:chohra-med/spec-harness-oss#v0.7.0 install <path> [new|integrate] [name]
spec-harness init <path> [new|integrate] [name]   # with no install: npx -y github:chohra-med/spec-harness-oss#v0.7.0 init <path> [new|integrate] [name]
spec-harness index <path> [--source <repo-relative-path> ...]   # with no install: npx -y github:chohra-med/spec-harness-oss#v0.7.0 index <path> [--source <repo-relative-path> ...]
```

The installer stages files and reports `PENDING`. The synthesis receipt and `spec-harness generate-agents --check <target>` (from a checkout, `bash <spec-harness>/bin/sh-gen-agents.sh --check <target>`; with no install, `npx -y github:chohra-med/spec-harness-oss#v0.7.0 generate-agents --check <target>`) establish structural and provenance readiness only. Declare overall initialization `READY` only after `spec-harness doctor <target>` reports `structural: READY` and a separate fresh reviewer checks that cited source lines support the rules and role bindings, package boundaries are respected, and no unresolved policy conflict remains. The reviewer ladder, with its non-Claude fallbacks, is in step 9 of `## Synthesis procedure`. Keep overall status `PENDING` if an independent review context is unavailable. This is separate from the first feature's goal, tests and release gates.

## Run sheet

This is the order of work. It works in any agent that has a shell and file tools. Where a tool has no slash commands, "run `/sdd init`" means: read the section `## 1. Check the route and project state` of `.claude/commands/sdd.md`, then this file. The section `## Synthesis procedure` below says what to derive; each step here points to it by step number and does not restate it.

**Before R0: inputs.** Settle these first. Ask the person once, in one message, for every item that is missing, including the mode and the project name. Use the defaults named here only when nobody answers; when the target cannot be found, stop and report `PENDING`.

- **Target path:** the project root, an existing directory. The installer refuses a missing directory and any path that contains `/second-brain/`. Default: the output of `git rev-parse --show-toplevel` from the current folder.
- **Mode:** `integrate` for an existing project, `new` for an empty one, `auto` to let the installer choose. Ask for the mode; use `auto` only when nobody answers (it is also what the installer uses when the mode is left out). `auto` picks `integrate` when the target has `.git`, `package.json` or `pyproject.toml`, and `new` otherwise.
- **Project name:** optional; ask for it in the same message. Default when nobody answers: the name of the target folder. It must not contain `/`, `\` or a line break. Always pass the mode when you pass a name: a lone word after the target that is not `auto`, `new` or `integrate` is read as the name and sets the mode to `new`.

- **Pick the CLI once.** Use the first form that works and keep it as `SH` for the whole run: (1) `spec-harness` on PATH; (2) `bash <checkout>/bin/spec-harness`; (3) `node_modules/.bin/spec-harness`; (4) `npx -y github:chohra-med/spec-harness-oss#v0.7.0`. Form 4 is a network download. It needs the person's yes, and it may be an older version than the installed procedure files. When none works, stop and report `PENDING`. `$SH` in the table stands for the chosen form: write it out in each command instead of using a shell variable. Run every command from the target root.
- **First init or refresh.** When `.claude/agents/.init-synthesis.json` exists, this is a refresh. Go to the section `### Refresh an initialized target after source changes` (under `## 1. Check the route and project state`) of `.claude/commands/sdd.md`. Do not run `index` first on a JSON inventory.
- **READY has three senses.** Use these words and no others: *checker READY* is the `READY:` line that `generate-agents --check` prints. *Structural READY* is `"structural": "READY"` in the `doctor` output. *Overall READY* is structural READY plus an independent review (R13) that accepts every claim. Report init as READY only when overall READY holds.
- **Every step ends with its check.** Fix a failed check or report it. Never move on with a failed check. After three failed rounds of the same check, stop and report `PENDING` with the output.

## Inputs and scope

- **Required:** the selected target root; its `ai_rules/context_map.md` or `ai_rules/project_inventory.json`; all applicable project instructions; the source files named as representative by the inventory.
- **Read first:** `AGENTS.md`, `RULES.md`, `CONTRIBUTING.md`, `ai_rules/`, `.memory/`, `.cursor/rules/`, `.agents/`, and the target `README.md`, following each instruction file's startup sequence. Then inspect project structure, package manifests and lockfiles, relevant tests/configuration, actual first-party source, and project-local installed skills plus capabilities explicitly exposed by the active client; when the client exposes none, use only reading files and running shell commands. Open only relevant skill candidates; do not scan unrelated global stores. Do not infer architecture from directory or dependency names.
- **Inventory:** run `spec-harness index <target>` first (the installed entrypoint is `node_modules/.bin/spec-harness index <target>` when using the npm package; with no install, `npx -y github:chohra-med/spec-harness-oss#v0.7.0 index <target>`).
  - Repeat `--source <repo-relative-path>` up to five times to choose up to five total sources; each must be a readable, regular, in-root, first-party source file with a supported source suffix and fit the existing read limits. Invalid or unsafe selections fail without replacing the current inventory. For a package with explicit selections, those paths are its representative sample; packages without selections retain the default sample.
  - Repeat `--exclude-dir <repo-relative-directory>` to leave generated or vendored directories (for example `ios` and `android` in an Expo app with prebuild) out of the scan; the inventory records them under `scan.excluded_directories`, and explicit sources under `scan.explicit_sources` (plus a limitation line the Markdown map shows).
  - Re-pass the flags on every index run, or run `index <target> --same-scope`, which reuses the options recorded in the inventory this run would replace (a generated `context_map.md`; `project_inventory.json` when `context_map.md` is customized; nothing when there is no `context_map.md`) and refuses to be combined with `--source` or `--exclude-dir`, and to reuse a Markdown map with a line outside the format index writes, or a map from an older index (no `Source HEAD` line) that records an `--exclude-dir` run, because that index did not name a folder the scan never reached; a plain refresh then prints a `SCOPE:` line, so run index once with the original options. A run that drops a recorded option, or whose default source sample differs from an inventory that records no `--source` paths, prints a `SCOPE:` line on stderr; the sample line matters only if an index that predates source recording built that inventory with `--source`. The exit code and the preview bytes are unchanged. A map refused for its format gives no `SCOPE:` line. The format check cannot catch everything: a map written by an older index run with `--exclude-dir`, in a tree holding a file name crafted to look like map lines, can still add an exclusion, so read what a `--same-scope` preview leaves out before writing.
  - Omitting `--source` preserves the existing default selection. Prefer `ai_rules/project_inventory.json` when it exists; otherwise consume a generated `ai_rules/context_map.md`.
  - Manifest parsing supports `package.json`, `pyproject.toml` and `composer.json` only; for `composer.json` it reads the name, script names and the `require` and `require-dev` package names, leaving out platform requirements such as `php` and `ext-*`; a required package named `<vendor>/framework`, `<vendor>/framework-bundle` or `<vendor>/product-<edition>-edition` is a stack signal. Keep other manifest formats visibly unsupported.
  - Read-only inventory paths/hashes are leads; open the actual source before making a claim.
- **Allowed writes:** fill only explicit Spec Harness scaffolds or owned generated regions; add missing per-package `RULES.md` and the named project skills (the core skills for the receipt's schema, plus technology skills) only when absent. Record conflicts and stop that artifact as PENDING. Do not replace existing user-authored policy, skill or role content. Do not change application source, dependency versions, external settings or release state.

## Synthesis procedure

1. **Map package boundaries.** Enumerate every inventory package path, manifest name/status, declared dependency names, scripts, representative sources, applicable instructions, exclusions and unsupported formats. An incomplete inventory or unsupported manifest stays `PARTIAL`; identify its effect instead of guessing.
2. **Read before deriving.** Open the applicable instructions and each package's actual representative source, plus its tests/configuration where present. Record the exact file and line span used for each observation. When correctness or currency requires outside guidance, consult official primary documentation, cite the URL and access date, and label that material a recommendation rather than an observed project fact. Cite the file that shows the claim, from the package's own source files. The representative sample is where reading starts, not the only file you may cite. When the network is blocked or not allowed, skip the outside lookup, mark that item `UNRESOLVED` and continue. Announce every outbound lookup first and keep it within the project's own data rules.
3. **Apply the reusable methods after inspection.** Read `ponytail.md`, `grill-me.md`, `package-finder.md`, `skill-finder.md`, `conventions.md`, `technology-profiles.md` and `standards.md` from `.claude/commands/spec-harness/` (source checkout fallback: `commands/`). Apply only methods relevant to observed package/task needs. Check tool availability and actual candidate contents; unavailable Context7 coverage/version evidence or Vercel skill provenance/license/runtime evidence stays PENDING for that decision. The standalone methods can run before a synthesis receipt or feature goal exists. Do not install packages or third-party skills.
4. **Derive package rules, each fact in its one home.** Follow `rules.md` (`Rule record` and `Rule layers`):
   - **Stack:** run `spec-harness stack <target>` (from a checkout, `python3 -I -B <spec-harness>/bin/sh_stack.py <target>`) to write `ai_rules/stack.md`. No other file may name a package version.
   - **Business:** read `.memory/` first. Fill the `Business`, `Goals`, `Users` and `Domain rules` sections of `.memory/10-product.md` from the memory bank, the README and the owner's answers; write domain rules as `BIZ-` rule lines. Do not guess a business rule from code.
   - **Memory kinds:** ask which optional memory kinds fit this project: `content` (voice and audience), `automation` (a pipeline) or `research` (sources). Code is the default and needs no kind file. Copy only the chosen kinds' files from `.claude/spec-harness/memory-kinds/<kind>/` (source checkout fallback: `templates/memory-kinds/<kind>/`) into `.memory/`, never over an existing file, and record the choice in `.memory/00-description.md`. The core `.memory/` files stay as they are; `.claude/spec-harness/docs/MEMORY.md` (source checkout fallback: `docs/MEMORY.md`) says where each fact lives. A kind file is a PENDING template until the owner fills it; a kind the project does not use is not copied.
   - **PR destination:** derive the selected destination from the project's cited policy, not a guessed branch. Carry that same destination into synthesized delivery rules for Before evidence, packet checks and ship checks. If policy does not establish it, record it as unresolved and ask the owner; retain existing defaults until a destination is established.
   - **Decisions:** record existing decisions, accepted conventions and overrides as `DEC-` rule lines in `.memory/60-decisions.md`, each with who decided and the date.
   - **Memory bank:** fill every core file in `.memory/` (`00-description`, `01-brief`, `10-product`, `20-system`, `30-tech`, `40-active`, `50-progress`, `60-decisions`, `70-knowledge`, `80-feedback`) from this project's evidence and replace each staged `PENDING:` line. Where there is no evidence yet, write `None recorded yet (YYYY-MM-DD).` instead of guessing. `spec-harness doctor <target>` counts a file as a scaffold when it is empty or still holds a `PENDING:` line, a `{{TOKEN}}`, an `_<placeholder>_`, `generated at init` or `No project-specific rules generated yet`.
   - **Baseline:** evaluate each pack `baseline-*.md` and copy applicable lines from `.claude/spec-harness/rule-packs/` (source checkout fallback: `templates/rule-packs/`) to `ai_rules/rules/baseline-<topic>.md`, keeping its markers and the rule lines that apply, byte for byte, plus the source-bound marker and a cited source line that shows where the pack applies. In v1 a pack is recommended, not required: adopt the ones that apply.
   - **Tools:** for each runtime, framework and high-impact package in the stack (`technology-profiles.md`), copy its tool pack when one exists and the stack version is inside its `applies` range. Without a pack, write `ai_rules/rules/tool-<package>.md` from official documentation for that version, each rule citing the URL and `checked YYYY-MM-DD`. Use only generic queries (package name, version, topic); never send project code, names or data. When the network is blocked or not allowed, skip the lookup, mark the tool pack or `tool-<package>.md` as `UNRESOLVED` and continue.
   - **Standards:** run `standards.md`. Look for signals (markets, locales, personal, payment or health data, an existing accessibility statement or certificate), then ask the owner once which named standards the company has (`in place`), must meet (`required`) or plans (`planned`), for example the European Accessibility Act with EN 301 549 for an app offered to consumers in the EU. Record each as a `STD-` line in `.memory/10-product.md` and carry it out with a `standard-<name>.md` module from a pack or from the official text. Init records commitments; it never certifies compliance.
   - **Conventions:** run `conventions.md` on the code. Show each repeated pattern to the owner as a proposal with a recommended answer; an accepted one becomes a project rule plus a `DEC-` line, a rejected one is dropped. Never write an unaccepted convention as a rule.
   - **Duplicates and conflicts:** merge a requirement found in several sources into one rule whose source tag lists every source. Settle a conflict by precedence (business, standard, decision, project, tool, baseline) with `overrides <ID>` on the winning rule; record anything precedence cannot settle in `rule_conflicts` and ask the owner.
   - **Package rules:** for each boundary, preserve authoritative policy and fill only empty sections or explicit generated scaffolds. Make rules specific to that package path. Separate `OBSERVED` behavior from `RECOMMENDATION`; label SOLID and performance heuristics when code does not establish them. Surface rule/code contradictions for human resolution. Do not copy a rule across a TS, mobile, Python, backend or other package boundary without evidence that it applies there. Keep volatile literals such as a test count out of rules and skills; state the command and the comparison instead, so the next ticket does not make them stale.
   - **Coverage and semantic review:** For each package, report one coverage table with pack or relevant documentation/design topic, package scope, disposition, adopted IDs or exclusion/unresolved reason, provenance class, evidence and applicable higher-policy resolution. Evaluate every shipped baseline and each topic relevant to the confirmed stack. For partial adoption identify each applicable line adopted and explain every remaining exclusion or unresolved line. Material unresolved applicability or policy prevents semantic acceptance; structural READY alone does not establish coverage. Distinguish observed policy, accepted convention and recommendation; never invent existing policy. A guarded refresh shows the proposed policy delta and preserves custom bytes and higher policy.
   - **Documentation surface:** preserve the project-selected API documentation surface and higher policy; offer stack-specific guidance only where the stack is demonstrated.
5. **Create the project skills.** Create the core skills from `.claude/spec-harness/methods/spec-harness-{architecture,performance,packages}.md` (source checkout fallback: `templates/project-skills/`), at `.claude/skills/<name>/SKILL.md`. A first initialisation (no `.claude/agents/.init-synthesis.json` in the target) creates five core skills (architecture, performance, packages, quality, conduct): the three above plus `spec-harness-quality` and `spec-harness-conduct` from `.claude/spec-harness/methods/spec-harness-{quality,conduct}.md` (same fallback), and writes schema 4 with those five (schema 4 is schema 3's policy ledger plus the rule layers in step 4; `generate-agents.md`; a ledger row for a `.memory/` source also records `text_sha256`, so ordinary memory edits keep READY). A guarded refresh of an existing schema-1 receipt keeps schema 1 and its three skills unless the user asks to adopt five. Then follow `spec-harness-tech.md` from the same directory to add one `spec-harness-tech-<technology>` skill for each major technology the source actually uses, at most five, each scoped to the packages that use it. On first initialization, create a skill only when its name is absent; preserve any existing name and report `CONFLICT/PENDING`. On a later guarded refresh, reuse or refresh an existing skill only when its prior receipt, source-bound marker, documented generated ownership and exact preimage all agree and no custom edit intervened. Otherwise preserve its bytes and report `CONFLICT/PENDING`. Each generated skill states package applicability, cites the supporting source lines, and carries an inventory-hash source-bound marker. A skill names the rule IDs it applies and links to `ai_rules/stack.md` for versions; it never copies a rule sentence or a version, so the Expo, React Native and router skills all follow one stack entry and one rule. ## Status contract

- `PENDING`: synthesis has not run, a conflict exists, a citation is absent/invalid, an output is a stub, a role binding is unresolved/stale, or the check did not pass.
- `PARTIAL`: some package evidence is unsupported or the inventory is incomplete. List covered and uncovered package paths; overall initialization remains PENDING.
- `READY`: all inventoried package paths have checked rules, the core skills for the receipt's schema, any technology skills and required fresh role bindings are checked without conflict, the synthesis receipt passes the structural/provenance check, `spec-harness doctor <target>` reports `structural: READY` (every file it checks present and filled: the startup files, the `ai_rules/` core rules, the `/sdd` route, the receipt and the ten `.memory/` files; a project inventory; the startup route written; the check READY), and the separate fresh semantic review accepts the cited claims.

The receipt checker can print `READY` for structural/provenance integrity while overall initialization remains PENDING pending semantic review. Overall `READY` does not mean a feature goal, test suite, human approval or release gate is complete.
